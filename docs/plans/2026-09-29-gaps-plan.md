## Phase 0: Protect the work

### 0.1 Commit, push and back up the code — **do first**
- **Gap:** the repo has 2 commits and **no remote**. The whole Club/Opening rewrite, the AI
  layer, the seed script and the tests (59 files) are uncommitted on one machine, and two
  Claude sessions have been editing the same tree.
- **Fix:**
  1. Create a private GitHub repo and add it as `origin`.
  2. Commit in reviewable chunks on a branch (`rewrite/club-domain`): models + middleware,
     controllers + routes, AI, seed + scraper data, tests, docs. Open a PR into `main`.
  3. From then on, one session or person per branch.
- **Done when:** `git status` is clean and the branch is on GitHub.
- **Status: partly done.** Committed in chunks on `gaps/plan-2026-09-29`. There is still
  **no remote**: creating the GitHub repo needs your account, so `git push` is left to you.
  Do that before you edit anything else.

### 0.2 Stop the seed script from damaging a real database
- **Gap:** `scripts/seed.js` has no production guard.
  - `--reset` runs `deleteMany({})` on every collection, including real users and applications.
  - Even without `--reset`, it creates 150 fake students and a demo login with a known
    password (`student@demo.joinclub.test` / `Student@123`).
- **Fix:**
  - Refuse to run when `NODE_ENV=production` or when `MONGO_URI` points at a non-local host,
    unless `--allow-remote` is passed.
  - Split the script: `seed:clubs` (clubs, club admins, super admin — safe for production)
    and `seed:demo` (fake students, openings, applications, the demo login — dev only).
  - Make `--reset` also require typing the database name to confirm.
- **Done when:** `NODE_ENV=production npm run seed -- --reset` exits without touching data.
- **Status: done.** The guard moved to `scripts/seed-guard.js`. `--allow-remote` replaces
  `--i-know-this-is-production`; `--reset` on a real database asks you to type the database
  name, and a closed stdin (CI) does not count as a match. `npm run seed:clubs` skips every
  dummy student, opening, application and event, and omits the demo login from the CSV.

### 0.3 Keep tests off shared databases
- **Gap:** `tests/api.test.js` connects with the normal `MONGO_URI` from `.env` and drops
  `joinclub_test` on that server. If `.env` points at Atlas, tests run against the production
  cluster.
- **Fix:** read `TEST_MONGO_URI` only (fail if unset), or use `mongodb-memory-server` so tests
  need no external database at all. Refuse to run if the database name doesn't end in `_test`.
- **Done when:** `npm test` passes with no `.env` present.
- **Status: done.** `tests/helpers/testDb.js` starts a throwaway in-memory MongoDB, or uses
  `TEST_MONGO_URI` when set (that is what CI does, with a service container). The suite
  deletes `MONGO_URI` from the environment, and refuses to run unless the database it
  actually connected to starts with `joinclub_test`. **A restore was needed: another session
  added pino-http, which writes its own request id to `req.id` and so collided with the
  authenticated user's id** (see the note at the end).

## Phase 1: Frontend contract (things the rewrite must not miss)

`TODO.md` Phase 3 lists the pages to build, but not these backend requirements added during
hardening. Without them the new frontend will fail in confusing ways.

### 1.1 Required client behaviour
Build these once, in a shared `api.js` (axios instance), not per component:

| Requirement | Why | How |
|---|---|---|
| Send `X-Requested-With: XMLHttpRequest` on every request | `app.js` rejects writes without it (CSRF guard) | `axios.create({ withCredentials: true, headers: { "X-Requested-With": "XMLHttpRequest" } })` |
| Restore the session on page load | Redux is empty after a refresh | Call `GET /api/v1/auth/me` in `main.jsx` before rendering routes |
| Handle `401` globally | Expired cookie, or sessions revoked by a password change (`tokenVersion`) | Response interceptor: clear user, redirect to `/login?next=…` |
| Handle `403` with `code: "MUST_CHANGE_PASSWORD"` | Seeded club admins are locked until they set a password | Interceptor redirects to the set-password screen |
| Email verification step | `apply` returns 403 for unverified students | After signup, show the OTP screen; show a banner until verified |
| Show `isOpen`, never recompute it | Server is the source of truth | Use the field as returned |

- **Done when:** a Playwright or manual run covers signup → verify → apply, a seeded admin's
  forced password change, and a refresh that keeps you logged in.
- **Status: already satisfied, not changed.** The concurrent frontend rewrite had already
  built `lib/api.js` with the CSRF header, the `/auth/me` restore and the 401 /
  `MUST_CHANGE_PASSWORD` interceptors. Signup now takes the AI consent checkbox (required,
  linked to `/privacy`) and shows the verify-email OTP step inline after registering; the
  banner remains as the fallback. A Playwright run of the three flows is still to do.

### 1.2 Deadlines mean "end of day, India time"
- **Gap:** openings validate `deadline` with `z.coerce.date()`. A date-only value from an
  `<input type="date">` (`"2026-10-05"`) becomes midnight **UTC**, so the opening closes at
  05:30 IST on the 5th instead of the end of that day. `event.controller.js` uses
  `setHours(0,0,0,0)` in the server's timezone (UTC on Render/Railway), which hides events
  between 00:00 and 05:30 IST.
- **Fix:**
  - Backend: if `deadline` is a date-only string, store `YYYY-MM-DDT23:59:59+05:30`. Compute "today" for
    events in `Asia/Kolkata`. Put the timezone in one helper (`utils/time.js`).
  - Frontend: show every date with `timeZone: "Asia/Kolkata"`, and label deadlines "closes
    5 Oct, 11:59 pm".
- **Done when:** a test opening with deadline `2026-10-05` accepts an application at 22:00 IST
  on the 5th.
- **Status: backend done, frontend to do.** The opening deadline fix already existed; the
  timezone is now one helper, `utils/time.js` (`TZ`, `istDateKey`, `startOfIstDay`,
  `endOfIstDay`, `istDayEnd`), used by the opening route, the event route and the event
  controller, which no longer cuts off "today" at UTC midnight. A test asserts a date-only
  deadline is stored as `2026-10-05T18:29:59.000Z` (23:59:59 IST). The frontend must still
  format dates with `timeZone: "Asia/Kolkata"`.

## Phase 2: Data, access and privacy

### 2.1 Validate uploaded file types
- **Gap:** `middlewares/multer.js` limits size but not type, and Cloudinary uploads use
  `resource_type: "auto"`. A "profile photo" or "resume" can be an HTML, SVG or executable
  file, served from a URL the site links to.
- **Fix:** add a multer `fileFilter` per field: images (`image/jpeg`, `png`, `webp`) for
  photos, logos and covers; `application/pdf` for resumes. Check the file's magic bytes, not
  just the browser-supplied MIME type. Upload images with `resource_type: "image"` and PDFs
  with `"raw"`.
- **Done when:** uploading `evil.svg` as a photo or `resume.html` returns 400.
- **Status: done.** Type detection by magic bytes is in `utils/filetypes.js`. One trap worth
  knowing: **multer calls `fileFilter` before the storage engine has read the bytes**, so
  `file.buffer` is empty there; the real check is a `checkTypes` middleware that runs after
  multer, and `fileFilter` is only a cheap first pass on the declared MIME type. Cloudinary
  uploads now use `resource_type: "image"` for images and `"raw"` for PDFs, and the buffer
  goes over directly instead of through a base64 data URI (which also let the vulnerable
  `datauri`/`image-size` dependency be removed). Tests cover the SVG, the HTML-as-PNG and
  the HTML-as-PDF cases.

### 2.2 Club admin lifecycle and yearly handover
- **Gap:** super admins can only list admins and reset passwords. Club leadership at PEC
  changes every year, but nobody can:
  - create or archive a club;
  - add, remove or replace a club admin;
  - deactivate an account.

  The data model also disagrees with itself: `User.club` holds one club, and `Club.admins[]`
  holds many admins.
- **Fix:**
  - Super-admin endpoints and UI: create/edit/archive club; invite an admin by email (sends a
    set-password OTP); remove an admin (bumps `tokenVersion` so they are signed out).
  - Add `User.active` (checked in `isAuthenticated`).
  - Pick one source of truth for admin ↔ club; keep `Club.admins` derived or drop it.
- **Done when:** a super admin can hand a club from last year's head to this year's head
  without touching the database.
- **Status: backend done, UI to do.** `User.club` is the source of truth and `Club.admins[]`
  is derived from it by `utils/admins.js`, which is the only place that writes it. New
  super-admin routes: `POST /admin/clubs`, `PUT /admin/clubs/:id`,
  `POST /admin/clubs/:id/archive`, `GET /admin/users`, `POST /admin/admins` (invite by
  email, unusable random password, set-password code emailed in the background),
  `POST /admin/admins/:userId/reassign` and `POST /admin/admins/:userId/active`.
  `User.active` is checked in `isAuthenticated`, `optionalAuth` **and `login`** — deactivating
  also bumps `tokenVersion`, so old cookies stop working. `Club.archivedAt` hides a club from
  the public lists and from `/clubs/:slug` while keeping its history. The super-admin screen
  (`/super`, tabs) covers all of it: create/edit/archive club, invite by email, move an admin
  between clubs, deactivate/reactivate, and a people search across accounts.

### 2.3 Privacy: consent, deletion, retention
- **Gap:** the site stores phone numbers, SIDs, branches, resumes and application answers,
  and sends student profiles and answers to Anthropic (helpdesk context, the answer checker,
  applicant summaries). There is no privacy notice, no consent for AI processing, no way to
  delete an account or export data, and chats are kept forever. India's DPDP Act 2023 expects
  notice, consent and erasure.
- **Fix:**
  - A short privacy page: what is stored, who sees it (club admins see applicants' profiles
    and answers), and that AI features send text to Anthropic.
  - A consent checkbox at signup; mark AI features clearly, and add a profile setting to
    opt out of AI applicant summaries.
  - `DELETE /api/v1/users/me` (removes the profile, anonymises applications, deletes chats) and
    `GET /api/v1/users/me/export` (JSON).
  - A retention rule: delete chat sessions after 180 days (TTL index on `updatedAt`).
- **Done when:** a student can read the policy, export their data and delete their account.
- **Status: done.** The notice text is in `docs/privacy-notice.md`
  (marked as a draft needing an operator name and contact). `consentAi` is taken at signup
  (required checkbox, linked) and revocable in the profile; `aiApplicantSummary` (default on) is the per-feature opt-out,
  and the applicant-summary endpoint returns `optedOut` instead of calling the model.
  `GET /api/v1/users/me/export` returns the account, applications and chats with no secrets.
  `DELETE /api/v1/users/me` deletes chats and the profile, unfollows the clubs, and
  **anonymises** the applications: answers dropped, applicant replaced with a placeholder id
  (not `null`, which would collide in the unique index) and `applicantDeleted: true`. Chat
  sessions and messages both have a 180-day TTL index. The `/privacy` page exists (footer +
  signup links) and the profile has a Privacy & AI card: consent + summary toggles, JSON
  export download, and typed-confirm delete.

### 2.4 Database backups
- **Gap:** no backup plan. Atlas's free M0 tier has no automated backups.
- **Fix:** a nightly `mongodump` (GitHub Actions cron or the host's cron) to private storage,
  keeping 14 days; or use a paid tier with snapshots. Test a restore once.
- **Done when:** a restore into a scratch database has been done and written down in
  `docs/runbooks/restore.md`.
- **Status: written, not yet proven.** `.github/workflows/backup.yml` dumps nightly at 02:30
  UTC, uploads a gzipped archive to a private S3 bucket with today's date in the key, and
  deletes anything older than 14 days. `docs/runbooks/restore.md` has the step-by-step
  procedure. **Two things need you:** the repository secrets (`MONGO_URI`,
  `BACKUP_S3_BUCKET`, `BACKUP_S3_PREFIX`, `BACKUP_S3_REGION`, and the AWS keys), and one
  real restore into a scratch database. Do that restore before you need it.

### 2.5 Application status history
- **Gap:** only the current status is stored. Students can't see when something changed; club
  admins can't see who shortlisted or rejected someone. This matters when several people
  run a club's account.
- **Fix:** add `history: [{ status, by, at }]` to `Application`, appended in `updateStatus`
  and `withdraw`. Show a timeline to the student, without names of who changed it. Show the
  full timeline to the admin.
- **Done when:** changing a status adds a history entry that appears in both views.
- **Status: done.** `history` is appended on apply, re-apply, withdraw and
  every status change. `GET /applications/mine` strips the `by` field, so the student sees
  what happened and when but not who did it — naming the admin would let a rejected student
  identify the person who rejected them. The admin applicants list keeps the names
  (`history.by` populated). Both timelines render in the UI: a dated history under each card
  on `/applications`, and a full timeline in the admin applicant panel.

## Phase 3: AI correctness and cost

### 3.1 Long interviews lose their beginning
- **Gap:** `ai.controller.js` loads only the last `HISTORY_LIMIT = 12` messages. A 10-question
  interview has about 21, so:
  - the final report's transcript is missing the early answers;
  - the interviewer can no longer see which topics it already asked, so it repeats them.
- **Fix:** for `interview` mode, load the whole session (it is bounded by `total`); keep the
  12-message cap for the helpdesk only.
- **Done when:** a demo-mode test with `total: 10` produces a report whose transcript includes
  Question 1.
- **Status: done, with a caveat on the test.** The loading rule is now one function,
  `loadHistory(sessionId, mode)`: the whole session for an interview, the last 12 for the
  helpdesk. (The old `2 * total + 4` heuristic was a guess at the same thing.) The test
  asserts the *loading rule* directly — an interview with 31 stored messages returns all 31
  and the helpdesk returns the last 12 — rather than the plan's original check, because
  **the demo-mode report is rule-based and contains no transcript** to inspect. The real
  transcript check needs a live `ANTHROPIC_API_KEY`; do it once before launch.

### 3.2 Log AI usage and cost
- **Gap:** nothing records token usage, so there is no way to see spend, spot abuse, or build
  the daily per-user budget that `TODO.md` 4.2 calls for.
- **Fix:** after each call, store `{ user, feature, model, input_tokens, output_tokens,
  cache_read_input_tokens, at }` in an `AiUsage` collection (read `usage` from the final
  message). Add a super-admin page with daily totals per feature. The per-user daily budget
  can then read from this collection.
- **Done when:** the admin page shows today's tokens per feature, and the cache-read count is
  non-zero on repeated helpdesk calls (proves prompt caching works).
- **Status: logging done, page to do, prompt caching not yet proven.** Every call in
  `ai/llm.js` records its token counts (including `cache_read_input_tokens` and
  `cache_creation_input_tokens`) into `AiUsage` via `ai/usage.js`, which is attributed
  through `withUsageContext` — one wrapping call per feature, so the helpdesk, checker,
  interview, per-answer scoring, follow-up chips and applicant summary are told apart.
  `GET /api/v1/admin/ai-usage?days=7` returns totals, per-feature, per-day and top-users
  (`?days`, capped at 30). **The cache-read count can only be confirmed against the live
  API**, and `performance-plan.md` 3.4 is what adds the cache breakpoints that make it
  non-zero. The admin screen exists as the AI usage tab on `/super` (totals, per-feature
  table, heaviest users, calls-per-day chart).

### 3.3 Chat edge cases
- **A failed stream leaves a duplicate question:** the user's message is saved before the model
  runs. When the model fails, a retry saves the same question again. Save the user message
  and the reply together after success, or delete the orphan in the `catch`.
- **Guests can make up earlier replies:** guest `history` accepts `assistant` turns from the
  browser. The risk is low because only public data is in context, but cap guest history at
  6 turns and strip `[[options: …]]` markers from submitted assistant turns.
- **Status: done.** The user's message is now saved only after the model has answered, and
  the `catch` deletes it if the save landed but the stream then failed, so a retry cannot
  duplicate a question. Guest history is capped at 6 turns, and `[[options: …]]` markers are
  stripped from submitted assistant turns so the browser cannot make the assistant offer
  choices it never made. A test asserts an injected marker never comes back as a real offer.

## Phase 4: Operations and reach

### 4.1 Continuous integration
- **Gap:** no CI.
- **Fix:** a GitHub Actions workflow on every PR runs these steps:
  1. backend `npm test` with a MongoDB service container;
  2. frontend `npm run lint` and `vite build`;
  3. `npm audit --omit=dev --audit-level=high`.

  Enable Dependabot for both `package.json` files. Add `"engines": { "node": ">=22.9" }`,
  since the test script uses `--env-file-if-exists`, which older Node versions don't have.
- **Status: done, pending the first run.** `.github/workflows/ci.yml` has the three jobs
  above, and `.github/dependabot.yml` watches both `package.json` files plus the actions.
  `engines` is set. The audit step is why `package.json` has an `overrides` block:
  `rate-limit-mongo` pins `underscore` to exactly `1.12.1`, which carries a high-severity
  recursion advisory; the override forces the fixed `1.13.8`, so
  `npm audit --omit=dev --audit-level=high` passes. `npm audit --omit=dev` now reports **0
  vulnerabilities**. This all needs a GitHub remote to actually run.

### 4.2 Error monitoring
- **Gap:** errors go to `console.log` only.
- **Fix:** Sentry (free tier) in both the backend (`errorHandler`, unhandled rejections) and
  the frontend (React error boundary). Strip cookies and request bodies from events.
- **Status: done.** `utils/sentry.js` initialises
  `@sentry/node` only when `SENTRY_DSN` is set, so nothing leaves the machine until you add
  a DSN, and `errorHandler` reports 5xx with the URL. `beforeSend` drops cookies, auth
  headers and request bodies. Unhandled rejections and uncaught exceptions are logged. The
  frontend has an `ErrorBoundary` around the app plus `lib/sentry.js`, which initialises
  `@sentry/react` only when `VITE_SENTRY_DSN` is set (PII off, no traces, request bodies
  stripped).

### 4.3 Rate limits survive restarts and scaling
- **Gap:** `express-rate-limit` uses its in-memory store. Limits reset on every deploy or
  restart, and don't work if the host runs more than one instance.
- **Fix:** use `rate-limit-mongo` (no new service), or Redis if one is added later.
- **Status: done.** All four limiters share a `RateLimitMongo` store, falling back to memory
  if Mongo is not connected yet or `RATE_LIMIT_STORE=memory` is set, so the app still boots
  without a database. The limiters also gained a `userId(req)` guard that only accepts a
  string: that is what stops a non-user value in `req.id` from silently disabling a limit
  (see the note at the end).

### 4.4 Email deliverability during recruitment season
- **Gap:** Gmail SMTP allows about 500 messages a day. Verification OTPs, password resets and
  (later) status emails during a recruitment week can exceed that. Nothing tracks failed
  sends.
- **Fix:** use a transactional provider (Brevo or Resend free tier) with SPF/DKIM on a real
  domain; log send failures; show "didn't get it? resend in 60 s" in the UI.
- **Status: failure tracking done, provider and resend UI to do.** Both Brevo and Resend
  speak SMTP, so switching is a change to `SMTP_*` and nothing else — the settings are
  documented in `.env.example`. Failed sends are recorded in `MailFailure` (30-day TTL) and
  logged, so a quota run-out is visible instead of silent. **The resend countdown is
  frontend work** (TODO Phase 2's OTP screen has a 60 s button already). This item is really
  waiting on decision 4 below: a domain to send from.

### 4.5 Link previews and search

- **Status: done, pending a deployment decision.** `routes/preview.route.js` serves Open

### 4.6 Images and content from pec.ac.in

## Two bugs found along the way, worth remembering

**pino-http hijacked `req.id`.** `pino-http` writes its own request id to `req.id`
(`req.id = req.id || genReqId(req, res)`), and this codebase uses `req.id` for the
*authenticated user's* id. Because the logging middleware runs first, every guest request
carried a numeric `req.id`, so `if (req.id)` was true for guests: `GET /openings` and
`POST /ai/chat` failed with `CastError → 400`, and — worse — the AI rate limiter keyed
guests on that number instead of their IP, so guest rate limiting was effectively off. Fixed
in `app.js` by moving the log id to `req.requestId` right after pino-http, and hardened in
`rateLimits.js` with a `userId(req)` helper that only accepts a string. If a request-scoped
library is ever added, assume it wants `req.id`.

**multer calls `fileFilter` before the file is read.** `file.buffer` is still empty inside
`fileFilter`, so a magic-byte check placed there silently rejects every real file. The check
has to be a middleware after multer; see 2.1.
